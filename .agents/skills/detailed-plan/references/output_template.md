# Implementation Plan Output Schema & Section Guidelines

Every plan generated by `detailed-plan` MUST follow this exact section structure in `implementation_plan.md`.

## Required Header Fields

Top-of-file metadata, before section 1:

- `Spec:` path to the linked task spec, if one exists. `none` otherwise.
- `Grounding:` path to the grounding artifact, if one exists. This is the
  authoritative path the implementation phase reads — do not derive it from
  the spec slug, which can differ when a spec was split from another. `none`
  when there is no linked spec or no grounding artifact.

## Required Section Structure

1. `Explanation`
2. `Plan Contract`
3. `High-Level Design & Component Changes`
4. `Case Discovery & Test Strategy`
5. `TDD Matrix`
6. `Failure-Class Coverage`
7. `Execution Queue`
8. `Verification`
9. `Assumptions / Blockers`
10. `Conventional Commit`

---

## Detailed Section Specifications

### 1. Explanation
Follow [.agents/workflows/explain.md](../../../workflows/explain.md). Start broad, then narrow.
For bugs show:
- `Confidence`: `ABSOLUTE`, `HIGH`, `MEDIUM`, or `LOW`.
- `Evidence`: Strongest reproduction boundary or log line.
- `Fix readiness`: `source-level fix ready` | `investigate first`.

### 2. Plan Contract
State:
- `Profile`: `COMPACT`, `STANDARD`, `ARCHITECTURE`, `INVESTIGATION`, `WORKFLOW_DOCS`.
- `Goal`: High-level purpose.
- `User impact`: who is affected and how.
- `Architecture decision`: `LOCAL_FIX_OK` | `SYSTEM_CHANGE_REQUIRED` | `INVESTIGATE_FIRST`.
- `Selected workflows/skills`: Explicitly state that execution enters `parallel-subagent-driven-development`.
- `Subagent waves`: List dispatched roles and explicitly record skipped roles as `not dispatched — lead preflight complete`. Include the Wave 1 spec-drift table when a task spec is linked.
- `Plan history`: Re-use or lessons from `detailed_plan_history.py`. For `STANDARD`/`ARCHITECTURE` plans linked to a task spec, append history entry:
  ```bash
  python3 .agents/scripts/detailed_plan_history.py append \
    --title "<title>" --goal "<goal>" --problem "<problem>" \
    --plan-fix "<fix>" --lessons "spec-drift: <roles>" --status planned
  ```
- `Integration test decision`: `REQUIRED` | `NOT REQUIRED`.
- `Failure-class coverage status`: `COVERED` | `CLEAN` | `N/A`, plus the `Failure-class source` from §6.
- `In scope` and `Out of scope`.
- `No-shim rule`: Explicit statement that contracts will be fixed at source.

### 3. High-Level Design & Component Changes
Describe component interactions, state transitions, logical file changes grouped by owner, permission enforcement points, and transaction boundaries.

### 4. Case Discovery & Test Strategy
- Subagents run, scopes, evidence, key conclusions.
- De-duplicated scenario ledger table (`Scenario ID`, `Spec IDs`, `Behavior`, `Evidence`, `Risk`, `Level`, `Coverage`, `Verdict`).
- Accepted tests with unique risk rationale.
- Merged/rejected candidates with reasons.

### 5. TDD Matrix
For executable changes:

| Scenario / Spec Link | Risk Prevented | Level | Real Boundary Exercised | Test Path / Existing Test | Red Command & Expected Failure | Green Contract | Refactor / Verification Gate |
| --- | --- | --- | --- | --- | --- | --- | --- |

Rules:
- Include ONLY final `KEEP` scenarios.
- Level MUST be `UNIT`, `CONTRACT`, `INTEGRATION`, or `E2E`.
- Exact command lines required; invoke Python with `python3`.

### 6. Failure-Class Coverage
Status header: `Failure-class coverage: <COVERED (N instances) | CLEAN (0 instances found) | N/A (Feature / non-bug task)>`.

State:
- `Failure-class source`: `SPEC (<spec path> §5b)` | `PLAN SWEEP (no linked task spec)` | `N/A (non-bug task)`.
- `Issue class`: Abstract contract or pattern failure.
- `Owner contract`: Component owner.
- `Sweep commands`: Structural `rg` query and subagent probe details. `n/a — spec-sourced` on the spec-linked path.
- `Related instances found`: Total sibling candidates.
- `Related instances fixed`: Every sibling instance included in plan scope.
- `Execution Queue coverage`: Each in-scope sibling mapped to its Execution Queue entry and TDD Matrix row. An unmapped sibling is a blocker.
- `New siblings found during preflight`: Any sibling absent from the spec. These escalate back to the spec as a new question — never a silent addition to plan scope. `none` when there are none.
- `Representative verification`: Targeted check command.
- `Non-matches / out of scope`: Rationale for candidates excluded.

### 7. Execution Queue

Two nested levels, and they answer different questions. **Groups decide what runs
concurrently. Tasks decide what one agent implements.** A plan that stops at the group
level leaves the execution workflow with no unit to dispatch, so it dispatches the group.

#### 7a. Groups

Tasks are grouped into task groups, each labeled `Independent (parallel-safe)` or
`Sequential (must follow <group>[, <group>...])` — name every group it gates on, comma-separated.

| Group | Label | Tasks | Rationale |
| --- | --- | --- | --- |

Thinking tiers are assigned **per group** by
[execution_grouping.md](execution_grouping.md)
§2, which is their sole owner. Do not restate the tier values here — one value, one
owner, per [single-source-of-truth.md](../../../rules/single-source-of-truth.md).

**A plan states no model, anywhere.** Not per group, not per task, not as a tier,
a level, or a floor. Which model a subagent runs on is owned solely by
[model-assignment.md](../../../rules/model-assignment.md),
and an implementer runs a standard-capability model in every plan without exception.

#### 7b. Tasks

Every group's tasks are enumerated as numbered headings, in execution order:

```text
## Task <N> — <short title>

- `Requirements`: the REQ / scenario IDs this task satisfies
- `Group`: the group ID this task belongs to
- `Files`: every file path this task creates, edits, or deletes
- `Consumes`: interface contracts this task depends on
- `Produces`: interface contracts this task establishes
- `Done when`: the finish line — a runnable command that fails now and passes
  when this task is complete, or a closed list of items that cannot grow
```

**`Done when` is required on every task** (`.agents/rules/sizing-agent-work.md`
§3.4). A task without one leaves its implementer to decide when it is finished,
and the three most expensive agents this repo has measured — 1,893, 1,757 and
1,002 turns — were each handed exactly that. Write the command out in full; if
you cannot, the task is not specified well enough to dispatch and the repair is
in the plan, not in the brief.

The heading is the task's identity; the group table above is only a summary. The
heading MUST be a numeric `## Task <N>` form, because the
`python3 .agents/scripts/task_brief.py PLAN_FILE N` that
`parallel-subagent-driven-development` Step 2
runs before every implementer dispatch extracts a task by matching
`^#+[ \t]+Task[ \t]+[0-9]+` and nothing else. A task authored only as a table row is
unextractable by it, and a non-numeric ID (`A1`, `G-A1`) is equally unreachable.

`Files`, `Consumes`, and `Produces` supply the like-named arguments of
`.agents/scripts/parallel_plan_grouping.py`'s
`Task(task_id, group_id, files, consumes, produces, advisory_label)`. That
`NamedTuple` has no defaults, so all six are required at the call: `task_id` is the
heading number and `group_id` the `Group` line. `advisory_label` has no task field
and is passed `None` — it exists to carry a *pre-existing* label into the labeler for
comparison, and a plan being labeled for the first time has none to carry.

**`Files` is the authoritative file set for a task.** The TDD Matrix's `Test Path`
column is a projection of it, never a second store: every path appearing there must
also appear in some task's `Files`, while `Files` additionally spans the source and
deletion work no scenario row covers. When the two disagree, `Files` is right and the
matrix row is stale.

**Granularity rule.** One dispatched implementer agent executes exactly one numbered
task and then returns. It never carries a second task. A live agent's remit is
never widened mid-task.

**RED and GREEN pair into one task.** Split across two tasks, the RED half commits a
failing suite, which the vendored task reviewer treats as a finding and turns into
fix-loop rounds that fix nothing.

#### 7c. Per-group notes the implementer needs

Optional, one short block per group, for the file-shaping context a task row cannot
express — a file already at its line ceiling, a fixture that must stay untouched, a
helper two tasks will share. Omit the subsection entirely when a group has none.

This is the *planning-time* half of a pair. Its runtime half is the group notes file
`parallel-subagent-driven-development` Step 2 defines, which each implementer appends
to as it makes further decisions. The orchestrator seeds that file from this
subsection before dispatching a group's first task, so both halves live in one place
the whole group reads.

### 8. Verification
Exact commands for targeted unit/contract checks, integration checks, and the project's own lint and type-check tooling — terminal step: a fresh run of the project's verify command configured at `[project] verify_cmd` in `.agents/config.toml`.

### 9. Assumptions / Blockers
List open dependencies or environment questions tagged `[decide-upfront]` or `[needs-evidence]`.

### 10. Conventional Commit
Provide one standard conventional commit message for human review.
